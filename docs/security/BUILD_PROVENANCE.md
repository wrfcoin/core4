# Build Provenance

## Rust toolchain

All supported Rust build paths use the exact toolchain declared in the repository-root
`rust-toolchain.toml`. The current pin is Rust 1.98.0 with `rustfmt`, `clippy`, and
`rust-src`, plus the `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` targets.
CI build and test commands use the committed root `Cargo.lock` through `--locked`.

The maintainers own toolchain updates. A version bump must be a dedicated, reviewable
change that updates `rust-toolchain.toml` and every explicit CI or container reference
together, passes `scripts/check_toolchain_pin.py`, and records any resulting lockfile or
compiler-behavior changes in the pull request. The nightly fuzz workflow is an explicit
auxiliary-tool exception; release and test artifacts continue to use the stable pin.

`scripts/check_toolchain_pin.py` is enforced by the pull-request-triggered
`ci-deploy-features.yml` workflow and by `ci-readiness.yml`, whose `preflight` job runs it on
every qualifying (paths-filtered) pull request as well as on the weekly schedule and manual
dispatch. (An earlier revision described `ci-readiness.yml` as scheduled/manual only; it gained
its pull-request gate in #2233/#2265.)
It rejects missing or divergent stable toolchain references, unpinned stable Rust
installs, unlocked Cargo build/test/check/clippy commands in active root workflows, and
Rust builder images that do not match the pin.

## Release artifact provenance (#2151)

Every binary `release-signing.yml` publishes carries a provenance statement — an
in-toto v1 `Statement` whose predicate follows the shape of
[SLSA Provenance v1](https://slsa.dev/spec/v1.0/provenance) — recording the exact source
commit, the workflow run that produced it, the builder identity, the toolchain, and the
artifact's own SHA-256 digest.

The toolchain and build command are **measured in the build job**, not declared by the
provenance job. Each build job runs `cargo build` from a bash array, records that same
array and `rustc -vV` output, and writes `<artifact>.buildinfo.json` with
`scripts/write_build_info.py`. That script refuses a toolchain whose `release:` is not the
pinned `RUST_VERSION`. `generate_provenance.py --build-info` copies both fields from that
sidecar and fails if it is missing or empty. The sidecar ships with the binary and is
covered by `SHA256SUMS`.

**What this proves, precisely, and what it does not.** The statement is generated by
`scripts/generate_provenance.py` from the CI run's own GitHub Actions context
(`generate-provenance` job in `release-signing.yml`, calling `release-provenance.yml` at the
*job* level — not as a step inside a job, which is the exact wiring mistake #312 found in an
earlier SLSA-generator attempt). This is **not** routed through
`slsa-framework/slsa-github-generator`'s keyless-signing / Rekor-transparency-log pipeline, so
it does not carry an independently, third-party-verifiable signature the way a full SLSA
Level 3 attestation does. What makes the *bundle* (binaries, `SHA256SUMS`, and every
provenance statement) verifiable is the same GPG key that has always signed WRFCoin release
artifacts: `SHA256SUMS` covers every provenance file's digest too, and `SHA256SUMS.asc` is
that GPG signature. Trust the GPG key exactly as much as you already did; the provenance
statements ride on that same trust anchor rather than adding a new one. Upgrading to the full
SLSA Level 3 generator pipeline is future work, not claimed here.

**Verifying an artifact against its provenance** (operator-facing, copy-pasteable):

```bash
# Download the artifact, its provenance statement, and the signed SHA256SUMS
# from the release page, then:
gpg --verify SHA256SUMS.asc SHA256SUMS   # confirms the WHOLE bundle's integrity
sha256sum -c SHA256SUMS                  # confirms every listed file's digest
scripts/verify_provenance.sh wrfcoin-node-linux-x86_64 wrfcoin-node-linux-x86_64.provenance.json
```

The last command recomputes the artifact's own SHA-256 and checks it against the digest the
provenance statement claims, and checks that the statement's subject name matches the
artifact's filename. It prints the recorded source commit and builder identity for you to
cross-check **by eye** against the audit report or release notes — it proves the artifact
matches its own statement, not that the statement's claims are independently attested (that
independent attestation is what the GPG signature over `SHA256SUMS` provides instead).

CI verifies this same chain against the **published** release (not the pre-publish build
artifact) as part of `release-signing.yml`'s `verify-signatures` job: it downloads the actual
release assets via `gh release download` and runs `scripts/verify_provenance.sh` against
every `*.provenance.json` it finds, failing the workflow if any artifact is missing a
statement or fails verification — "signing that nobody verifies is a no-op" applies to
provenance exactly as much as to the GPG signatures.

`scripts/test_generate_provenance.py` covers: subject digest matches the real artifact hash,
subject name is the artifact filename, statement/predicate types are the documented ones,
source commit/repo are recorded verbatim, a missing artifact is an error rather than a
fabricated statement, and `verify_provenance.sh` accepts a matching artifact while rejecting a
tampered one, a filename mismatch, a missing provenance file, and a provenance file with more
than one subject.
